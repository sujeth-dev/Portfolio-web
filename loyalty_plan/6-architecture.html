CMulti-tenant isolation

One database. Many restaurants. Zero leakage.

Tenant isolation is enforced at the database layer, not at the API layer. Every table carries restaurant_id. Row-level security policies guarantee a query for Restaurant A can never read Restaurant B's data — even if application code makes a mistake. 

-- Every row carries restaurant_id, indexed for fast filtering
CREATE TABLE customer (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  restaurant_id uuid NOT NULL REFERENCES restaurant(id),
  phone         text NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (restaurant_id, phone)
);

-- RLS policy: only see your own restaurant's customers
ALTER TABLE customer ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON customer
  USING (restaurant_id = current_setting('app.tenant_id')::uuid);

-- API sets the tenant context for the connection
SELECT set_config('app.tenant_id', '4f2e...', true);
Strategy
Shared DB, RLS

Cheaper than schema-per-tenant. Postgres RLS is battle-tested. Switch to schema-per-tenant only when a single restaurant exceeds 100k customers.

Subdomain
loop.app/r/<slug>

Path-routed in MVP1, faster to ship. Custom subdomains (filterandco.loop.app) in Pro tier, P2.

Brand assets
Per-tenant CDN path

Logo/hero image lives at /r/<slug>/logo.png. Cached forever, bust on update.

DThe five critical event flows

1 · QR scan → first visit

The most-traversed path. Must work without internet on the restaurant side, on first-load with a cold cache, in <1s perceived latency.
phone
Customer scans QR, opens /r/filter-and-co?t=tableA
API
GET /api/v1/r/:slug/landing — fetch brand_config + loop_config. ~200ms target.
phone
Customer enters phone. POST /api/v1/auth/start
queue
Enqueue whatsapp.send.otp — does not block. Customer sees "code sent" instantly.
worker
Picks up job, calls BSP, OTP arrives on WhatsApp in ~5s.
phone
Customer enters OTP. POST /api/v1/auth/verify → JWT issued.
API
Inside transaction: insert customer (idempotent on phone), insert visit, create journey (L1, progress=1), insert pending welcome message.
queue
Enqueue whatsapp.send.welcome.
phone
Welcome screen renders with 1/5 already counted. Total perceived time: ~30s.

2 · Reward redemption at counter

Must succeed even when the venue's wi-fi is down. Validates against a local cache, syncs when back online.
customer
Shows 6-digit code BREW-8K4 on phone.
counter
Staff enters code on counter PWA. Validates against local IndexedDB cache (synced every 5 min).
counter
If online: POST /api/v1/redeem. Server marks reward.redeemed_at, redeemed_by_staff, returns confirmation.
counter
If offline: store pending redemption in IndexedDB queue, show green tick anyway. Sync on reconnect.
db
On sync: idempotent merge. If code was already redeemed elsewhere, surface conflict to admin (rare).
queue
Enqueue reward.next_journey.unlock for customer — keeps loop alive.

3 · Activity submission → verification

Customer expectations are instant. Real verification is async with a 2-hour SLA tracker.
customer
Uploads screenshot or pastes URL. POST /api/v1/activities/submit
API
Insert activity_submission with status=pending, sla_due_at = now() + (2h or 6h by type).
queue
Enqueue activity.notify.admin → WhatsApp ping to restaurant owner.
customer
Sees "Received — your reward unlocks within 2 hours of approval."
admin
Reviews in queue, taps Approve. PATCH /api/v1/activities/:id
API
If approved → insert reward, enqueue whatsapp.send.reward_unlocked. If rejected → enqueue rejection notice.
cron
Every 15 min, scan for submissions past sla_due_at — escalate to admin's WhatsApp.

4 · Trigger fan-out (60% nudge, win-back, etc.)

A scheduled scan finds customers in the right state and queues a single message each. Idempotent, opt-out aware.
cron
Hourly: find customers at exactly 60% of an active journey who haven't been nudged yet. Find lapsed customers crossing day 30/60/90.
db
Query is restaurant-scoped, indexed on (journey.progress, journey.target). Returns batches of N.
API
For each: check opted_out, check daily message cap (max 2/day), record nudge_sent_at on journey to prevent duplicates.
queue
Enqueue whatsapp.send.<trigger> with template_id + variables.
worker
Sends via BSP. Records message row with cost_paise. Updates status on delivery receipts.

5 · POS / payment webhook ingest

External event arrives. We never trust it blindly — verify signature, normalise, dedupe, then act.
ext
Razorpay or Petpooja POSTs to /api/v1/webhooks/<adapter>
API
Verify HMAC signature. Reject 401 on mismatch. Insert integration_event row with raw_payload.
queue
Enqueue adapter.<name>.process.
worker
Adapter-specific normaliser: extract customer phone, bill_amount, items. Match or create customer.
db
Insert visit with source=payment or pos. Apply same reward logic as QR-scan visit. Loops progress, triggers fire.
worker
On adapter error: store error, retry with exponential backoff (max 5). Alert if >5% failure rate over 1h.

GDeployment & operations

Release engineering

  • Deploy windows · automated block 12–3 PM, 7–11 PM IST every day
  • API versioning · /v1, /v2, /v3 — last two always live (60-day deprecation)
  • Feature flags · per-restaurant toggles via simple table — pilot on 1 before all
  • Staged rollouts · 10% traffic → 50% → 100%, auto-rollback at > 0.5% error rate
  • Status page · public, the trust signal
  • On-call rota · 2-person team, alternating weeks, Sentry → WhatsApp alert

Security & data

  • India residency · DB + storage pinned to ap-south-1, DPDPA-compliant
  • PII minimization · phone only at signup; name/birthday opt-in after visit 2
  • One-click export · CSV download from admin, no exit fees, no delays
  • Opt-out · STOP reply via WhatsApp instantly stops all comms
  • Retention · inactive 2y → anonymised; offboarded restaurant → 90-day grace then deleted
  • Secrets · BSP keys, Razorpay keys in vault, per-tenant where possible
