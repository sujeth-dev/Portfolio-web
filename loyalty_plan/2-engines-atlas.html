01

Identity

Knows who every customer is, across every touchpoint, with phone number as the universal anchor.

MVP1 · core

What it does

  • Phone OTP signup via WhatsApp (60s flow)
  • Single customer record across visits, outlets, rewards
  • Gradual profile enrichment (name, birthday) collected after 2nd visit
  • Phone-number transfer flow (SIM change, lost number)
  • Cross-outlet visit pooling for multi-location brands (P2)

Why it works

Phone is the only identifier in India that's universal, WhatsApp-bound, and survives churn. No email, no app login, no password. Identity is solved on Day 1 — the rest of the platform sits on this anchor.

Edge case

Customer changes phone number. Old record sits, new record starts. Admin needs a one-tap merge flow with OTP-verified ownership of new number.

02

Customisation

Controls how each restaurant looks and behaves — fully white-labelled, config-driven, no per-restaurant code.

MVP1 · differentiator

What it controls

  • Logo, brand colors, hero image, custom font (P2)
  • Welcome copy + voice tone
  • Loop config (visits to milestone, reward item, expiry)
  • Activity set (which 3 active at a time)
  • WhatsApp template variables (restaurant name, reward name)
  • Operating hours, off-peak windows, day-of-week bonuses

Why it's the moat

Reelo looks like Reelo. Petpooja Loyalty looks like Petpooja. Loop looks like your restaurant. This is the single biggest reason premium restaurants switch from generic loyalty tools.

Design rule

Everything restaurant-specific lives in a config table. Adding a new restaurant is an insert, not a deployment. Preview-before-publish for all branding changes.

03

Reward

Decides when and what reward a customer earns. Behavior change system, not a discount system.

MVP1 · heart

The 4 reward buckets

  • Visit + time — every trigger fully automatic (timestamp, off-peak, streak, birthday, group)
  • Spend-based — self-entry (auto, unverified), payment redirect (auto, verified), bill photo (manual, slow), POS webhook (perfect, P2)
  • Activity-based — referral auto, everything else manual until P3 API access
  • Product-based — fully automatic but locked until POS integration (P2+)

The 4-layer loop system

  • L1 entry loop — 5 visits, free item. Starts at 1/5 (endowed progress)
  • L2 engagement — activity rewards unlock after L1
  • L3 habit — evolving category loops (brunch, cocktail, weekend)
  • L4 status — non-transactional access, recognition, regulars board
The universal rule

If you can't name the behavior a reward is changing, remove the reward. Loop is a behavior change system — every reward must drive a visit, increase spend, or amplify marketing.

L1 + 3 activities L2 + L3 + spend tiers L4 + variable surprise rewards

04

Flow

Manages what the customer sees and feels at every step — the rendered experience.

MVP1 · UX

The 9 customer-facing states

  • QR landing (pre-signup) — hook + one field
  • OTP verification — WhatsApp-first
  • Welcome moment — 1/5 already counted, celebration
  • Dashboard — progress bar, 3 activities, current rewards
  • Activity submission — instant ack, async verification
  • Reward unlocked — full-screen celebration
  • Coupon screen — code + restaurant + reward name
  • Loop completed — new journey unlocks
  • Lapsed / win-back — Day 30/60/90 sequences

The 8 killers it prevents

Empty progress states. Too many activities. No feedback after submission. Rewards too far away. Discount-only programs. Complicated redemption. Program staleness. Rewarding what customers do anyway.

Operating rule

Max 3 active activities. Progress bar always visible. Every action gets immediate acknowledgement, even if real verification is async. Offline-cached PWA so dashboard works without signal.

05

Verification

Confirms visits, activities, and redemptions are real — the hardest engine, the slowest to fully automate.

Evolves per phase

3 verification problems

  • Visit verification — QR → bill entry → staff confirm → POS webhook. Progressive solving.
  • Activity verification — manual MVP1, URL submission P2, third-party API P3 (fragile).
  • Coupon redemption — 6-digit UUID, phone-bound, offline-cacheable, single-use.

The verification ladder

  • Automatic — timestamp, off-peak, streak, birthday, payment, POS, referral
  • Light manual — staff one-tap (event check-in, group seating)
  • Medium manual · 2h SLA — Google review, Zomato, Instagram reel/post
  • High urgency · 6h SLA — Instagram story (24h disappears)
The honest limit

Social content verification will always need a human eye. Authenticity can't be fully automated without invasive API access. The smart move: make activity rewards proportional to the verification effort, and add trusted-customer auto-approve (P2) to reduce admin load over time.

06

Communication

Sends the right message to the right person at the right time. WhatsApp utility tier as the backbone.

MVP1 · backbone

The 5 mandatory triggers

  • T1 — Welcome · instant on first scan
  • T2 — 60% nudge · "two more visits and..."
  • T3 — Reward unlocked · instant on milestone
  • T4 — Expiry warning · 5 days before
  • T5 — Win-back Day 30 · gentle return

The channel stack

  • Browser push — free, always-on layer
  • WhatsApp utility — ₹0.35–0.60 / msg, 5 automated triggers
  • WhatsApp marketing — restaurant-paid via credits
  • SMS — silent fallback when WhatsApp fails
  • Email — admin reports only
External fragility

Meta controls WhatsApp API. Templates need pre-approval (1–7 days each). Submit all 7 MVP templates before launch day. Maintain primary + backup template for every type. Async queue prevents Friday-night load spikes from killing check-ins.

5 triggers + shared WABA number Manual campaigns + segmentation Per-restaurant WABA number
07

Integration

Connects to outside systems — POS, payments, social. The engine that unlocks every other engine's ceiling.

Grows over phases

The adapters (over time)

  • Razorpay / payment redirect — MVP1 — spend capture
  • WhatsApp BSP (Interakt/AiSensy) — MVP1 — comms
  • Petpooja webhook — P2 — visit + spend
  • UrbanPiper — P3 — multi-channel orders
  • Google Places review — P3 — activity auto-verify
  • Instagram Graph API — P3 — story/post check

The fragility doctrine

Every adapter is a dependency on someone else's system. Petpooja changes their API, our adapter breaks. Meta changes WhatsApp policy, comms is affected.

Design rule

Every adapter goes through an internal abstraction (VerificationService, CommsService). Every external dependency has a manual fallback. Health monitoring with alerts before restaurants notice degradation.

Analytics

Reads everything. Writes nothing. Tells the restaurant what's working — and tells us what to build next.

MVP1 · basic

The 3 restaurant numbers

  • Loop completion % · target > 40%, below 25 = reward too far
  • Return rate · target > 50%, below 30 = welcome broken
  • Redemption rate · target > 60%, below 40 = rewards not compelling

The platform-level metrics

  • Restaurant retention (renewal at month 6)
  • Restaurant ARPU + WhatsApp credit usage
  • Per-engine error rates + SLA hits
  • Aggregated benchmarks per restaurant type (Koramangala average return rate, etc.)
The monthly report

Every restaurant gets a WhatsApp+email digest on the 1st: new members, return visits, rewards redeemed, estimated revenue from loyalty customers. This single artifact is what makes month-6 renewal a no-brainer conversation.
